# Phase 1 financial contract

Customer and supplier receipt creation accepts an optional `Idempotency-Key` header (8-128 letters, digits, dots, underscores, colons or hyphens). Existing integrations without the header remain compatible, but must not blindly retry an unknown outcome. Updated web and mobile clients send a persisted key for each payment intent.

Keys are scoped to the authenticated actor and operation (customer versus supplier payment), hashed with SHA-256 and retained durably in the new V11 table. The canonical payment payload is fingerprinted. Identical retries return the stored receipt DTO with HTTP 200 and one financial effect, including after the balance has changed. A changed payload returns 409. Reversing a receipt retains its request record; retrying that key returns 409 instead of recreating the payment. Keys have no automatic expiry. A key is not an authorization token: ownership and role checks still apply before replay.

Clients persist the intent before sending it, disable duplicate submission, and reuse its key after a lost response or reload. They retain uncertain outcomes until retried unchanged. A definitive validation/conflict response permits corrected data with a new key. Acknowledged receipts clear the local intent. Customer web storage is scoped to actor/order, supplier web storage to actor, and native storage uses AsyncStorage for payment intents; native authentication storage remains unchanged.

Financial mutations use READ_COMMITTED transactions. Customer mutations lock the order, then current receipt rows/request state, then product rows in ascending ID order when needed. Supplier mutations lock distributors in ascending ID order, then the purchase order, receipt/request state, and sorted products. Refreshing locked entities avoids reusing mapper-loaded stale state. Distributor edits and quotation conversion/edit paths also serialize their shared aggregates. Existing product optimistic versions remain in force. Lock timeouts/deadlocks and stale writes return a controlled 409; clients must review/refresh and retry the same uncertain payment intent. There is no blind automatic server retry.

Receipt insertion/reversal, header balances, derived payment status, idempotency record and audit event commit together. Paid amount must equal the current receipt sum; balance must equal total minus that sum. Legacy header discrepancies block mutation with 409 for explicit reconciliation. Status is UNPAID for zero receipts, PAID when fully covered, otherwise PARTIAL. A manual enum cannot assert payment. Reducing a total below recorded receipts, cancelling a paid order or deleting a paid order requires reversing/reconciling receipts first. Existing authorized receipt reversal remains audited; this phase introduces no refund ledger or automatic bank refund.

Reservation changes compare aggregated product quantities before and after each order mutation. PENDING holds no stock; CONFIRMED/PROCESSING/SHIPPED/DELIVERED reserve stock. POST, PUT, PATCH, edits and cancellation use the same delta, so repeated statuses do not deduct or restore twice. Quotation conversion creates a PENDING order. Repeated product lines aggregate before stock validation. Insufficient stock rolls back the entire transaction.

Supplier advances continue to be supported. Supplier outstanding equals received purchase totals minus all recorded supplier payments, including standalone payments. An advance may make outstanding negative. Receiving a prepaid purchase adds its full total to outstanding; subtracting its remaining balance would count the advance twice. Receipt application and stock addition occur once under the purchase lock. This retains the existing partial-quantity receipt workflow; it does not introduce a new stock movement ledger.

## Historical reconciliation and rollout

Apply V11 through Flyway with schema validation enabled; retain every earlier migration and checksum. Roll out the backend before clients sending keys. Old clients remain supported, with the retry limitation above.

Run `backend/scripts/phase1-reconciliation-report.sql` read-only against an authorized snapshot/reporting connection. Export the discrepancies and associated receipts, source invoices and audit events. Nonnegative stock alone cannot detect the historical F02 inflation: compare source documents and a physical count.

A finance owner must classify duplicate/missing receipts versus incorrect headers and approve each proposed correction. Preserve genuine receipts; do not invent ledger entries to make headers agree. Prepare a separately reviewed, narrowly scoped transaction with expected-old-value guards and before/after exports, backup and rollback procedure. Stock corrections require a reviewed physical count and an authorized audited stock adjustment. Execute only with separate authorization against the intended environment, rerun the report and retain signoff. No historical repair or real business data mutation is included in this phase.

## Verification

`cd backend; mvn -Pmysql-it verify` runs the ordinary suite and `FinancialIntegrityMySqlIT`. Set `PHASE1_MYSQL_URL`, `PHASE1_MYSQL_USERNAME`, `PHASE1_MYSQL_PASSWORD` and `PHASE1_JWT_SECRET` in the process environment. The URL must target an isolated `phase1_` database on real MySQL. Provision a trusted hostname-matching certificate and use `sslMode=VERIFY_IDENTITY`; do not weaken TLS. The test account needs schema/migration privileges and access to `performance_schema.data_lock_waits` and `data_locks` to coordinate actual blocked transactions. Use a dedicated disposable instance, never a shared business database. The suite inserts synthetic fixtures and does not automatically delete historical records.

For clients, run the newly built backend on port 18091 against an isolated database and Vite on 5181 with `VITE_API_BASE_URL=http://localhost:18091/api`; allow that origin in backend CORS. Run `cd automation-tests; npx playwright test -c playwright.phase1.config.js`. The setup bootstraps only an empty test database, or uses generated credentials in ignored `audit-artifacts/phase1-client-session.json`. Evidence and remaining platform limitations are recorded in `REMEDIATION-TRACKER.md`.
